# Simple campaign contract — coordinated breaking revision

This is the authoritative implementation contract for shared package **0.2.0**.
The final source commit and package digest MUST be taken from the accompanying
handoff, once published. Operator and Harness MUST require an exact matching
package digest. The former attempt body and `engine.request_stop` are not supported
by this revision. Transport envelopes, sequencing, deadlines, restore binding and
no-replay semantics remain unchanged.

## Ordinary execution

The model tool `attempt_execute` maps directly to `engine.attempt_execute`:

```json
{"origin":"scenario","operation_id":"invoke","scenario_id":"configuration","input":{"encoding":"json","value":{"prompt":"Reply exactly QA_CONFIG_OK. Do not call tools."}}}
```

`origin`, `operation_id` and `input` are required. The operation is a permitted target
capability ID, never a URL or executable. `origin` MUST be explicitly `scenario` or `exploratory`. Scenario origin MUST include
a `scenario_id` from the submitted bundle. Exploratory origin MUST NOT include
`scenario_id`. Missing origin MUST be rejected, never inferred. Invalid combinations
MUST be rejected before target dispatch using the existing INVALID_ARGUMENTS error,
a field path, effect_state none and correct-and-resubmit. Correction uses a new
operation ID; exact delivery duplicates remain idempotent. Scenario policy still
applies. The outer envelope operation ID is generated by Harness runtime, not the
model. It is distinct from the body target operation ID.

Input MUST be exactly one of:

- `{"encoding":"json","value":...}`: JCS canonical JSON, application/json.
- `{"encoding":"utf8","text":"..."}`: exact UTF-8, text/plain unless an explicit
  `media_type` is supplied.
- `{"encoding":"base64","data":"...","media_type":"..."}`: canonical padded
  base64, decoded exact bytes and explicit media type.
- `{"artifact_receipt":"..."}`: an already committed payload or carrier artifact
  in this campaign. The host resolves its descriptor and verifies bytes and purpose.

Direct decoded input MUST be at most **32,768 bytes**, with JSON nesting at most
**16 containers** (scalar depth zero), and obey the smaller target input limit.
The entire request MUST fit the registry limit. Larger inputs use artifact
publication. Unknown fields, duplicate keys, noncanonical base64 and invalid
supplied values MUST be rejected, not repaired. Operator MUST retain effective
bytes, their identity and the resolved plan before dispatch. Retention failure
MUST prevent dispatch.

Operator assigns attempt ID, monotonically increasing submission index, thread,
generation, release binding and request correlation. Rejected host submissions
may consume an index; local validation failures do not allocate host attempts.
Exact duplicate delivery MUST reuse its retained result and cannot execute again.
Changed content under an existing operation ID MUST conflict.

`parent_attempt_receipt_id` optionally selects a real prior execution receipt;
Operator derives thread, parent identity and generation from its verified lineage,
including permitted restore lineage. A rejected submission has no execution
receipt and cannot be used as a parent or evidence. Root generation is one.

Omitted `pre_actions` means `[]`; omitted `observation_selection` means
`{"mode":"all-permitted"}`. Nonempty setup requires `injection_input` using the
same input alternatives, resolving to canonical application/json. `input` remains
the actual invocation input. Operator supplies the injection payload digest.
`retain_injections` defaults false and is only valid with nonempty setup. Action
IDs are handles for optional injection cleanup; they are not attempt receipts.
Existing capability, selector, fidelity, ownership, budget and cleanup checks MUST
remain enforced. Optional caller principal is accepted only when exposed by the
target contract. No caller-supplied counters, descriptors or binding are accepted.

Results retain the existing execution outcome, target-contact, cleanup, retry and
feedback fields. `receipt_id` means an authoritative executed-attempt receipt;
`attempt_id` is host bookkeeping. Predispatch rejection MUST NOT produce an
execution receipt. Observation reads MUST retain current campaign, visibility,
availability, integrity and range checks. Completed target execution alone does
not establish objective success.

## One finish operation

The model tool `finish` maps directly to `engine.finish`:

```json
{"finish_reason":"objectives-addressed","assessment":{"summary":"The target returned the expected marker.","objectives":[{"objective_id":"configuration","outcome":"supported","summary":"Observed QA_CONFIG_OK.","attempt_receipt_refs":["receipt-returned-by-Operator"]}]}}
```

The request MUST include `finish_reason` and exactly one of `assessment`,
`artifact_receipt`, or `unavailable`. An assessment artifact MUST be a committed
`conclusion`-purpose application/json artifact containing the **assessment draft**,
not a caller-constructed binding or conclusion record. Direct assessments obey
ordinary request bounds; artifact assessments remain bounded to 1 MiB.

Assessment requires only `summary` and `objectives`. Each objective specifies
its ID, outcome and summary. Omitted collections, including reference arrays,
hypotheses, claims, coverage and uncertainties, resolve to empty arrays. Omitted
assessment status resolves to `partial`; this conservative default conveys no
claim of objective success. Explicit invalid values MUST fail. Operator records
these resolved defaults and its own current binding in the retained conclusion.
It MUST NOT invent outcomes, hypotheses, claims, evidence or history.

Supported outcomes require execution evidence; zero-attempt assessments MAY use
empty references with `not-tested`, `not-observed`, or `inconclusive` outcomes.
Hypotheses defined locally are available throughout the assessment irrespective
of order, without earlier registration. Historical references MAY resolve through
campaign records. Unknown references, duplicate IDs, self-parenting, cycles,
invalid evidence, unavailable ranges and incorrect receipt categories MUST fail.
Optional historical `record_append` supports hypothesis/progress/lineage/coverage;
it does not register a conclusion for finish.

When no assessment can be constructed, use for example:

```json
{"finish_reason":"harness-error","unavailable":{"reason":"invalid-call-limit"}}
```

Operator MUST validate and retain the assessment and its reference checks before
accepting finish. An invalid finish returns a correctable rejection and MUST NOT
claim acceptance. Acceptance closes execution and returns `status: accepted`,
`assessment_state: committed|unavailable`, `execution_admission: closed`,
`finalization_status: pending`, and the existing five-second exit requirement.
Acceptance MUST NOT imply cleanup completion. Existing campaign status, completion
receipt and reports convey final cleanup results. Duplicate delivery is idempotent;
interrupted finalization never replays a campaign. Deadlines and owned cleanup MUST
remain enforceable independently of whether any assessment was produced.

## Diagnostics and Harness handoff

Operation errors MAY include `diagnostic`, validated by workflow-diagnostic.schema.
It contains source, stage, stable reason, bounded message, execution state and
resubmission safety, with optional field path, identifier, correction and explicit
omissions. Producers MUST select safe facts; credentials, bodies, prompts and
unrestricted provider errors MUST NOT be copied into these fields. Omissions
identify fields and one of sensitive/oversized/unavailable/invalid.

Harness runtime MUST use `engine.diagnostic_report` to retain local validation and
stopping diagnostics. This is not a model tool. Its optional `stopping` includes
condition, observed count and configured limit. Reports are attributed to Harness;
Operator's actual dispatch and cleanup records remain authoritative. On invalid
call exhaustion Harness MUST report the last error and counts, then use finish
with the explicit unavailable reason if it cannot produce an honest assessment.
Existing loop limits MUST NOT increase. Host reporting MUST preserve the primary
cause through generic worker failure, with cleanup failures recorded separately.

Model-facing local rejections MUST use the existing operation-error object with
`code: INVALID_ARGUMENTS`, `effect_state: none`, `disposition: correct-and-resubmit`,
and a `diagnostic` whose source is `harness-local`. Tool/call correlation stays in
the model protocol message. No execution receipt is attached. Host errors preserve
their code and source. Runtime reports MUST include the last tool/call identities;
Operator retains only safe selected facts plus a digest of the original report,
never submitted diagnostic message/identifier/correction prose.

Harness MUST validate arguments before sending, keep IDs product-owned, identify
duplicate keys, and preserve diagnostic paths and correction advice. Runtime
state, never identifier prefixes alone, determines receipt categories. Tool
feedback MUST distinguish local rejection from host rejection and whether dispatch
occurred. A new corrected call uses a new outer operation ID. Successful restore
still skips the remainder of the current model-response batch.

Provider declarations are projections. Runtime schemas and semantic validators
remain authoritative for cross-field and bounded JSON rules omitted by provider
schema restrictions. All codecs MUST describe the same accepted operation.

## Verification and delivery

Shared fixtures MUST cover direct/artifact inputs, explicit defaults, invalid
references, zero-attempt finish, optional local hypotheses and malformed values.
Go and Python MUST agree. Operator process tests MUST verify execution → observation
read → finish, retention-before-dispatch, duplicate finish, correction, invalid-call
exhaustion, cleanup and exported diagnostics using controlled local peers. A real
Harness process integration requires the matching separate Harness implementation.
No live provider reliability is established by controlled tests. Record schema
bytes, required model fields and ordinary workflow call counts against the prior
contract. Publish no release as part of this change.
